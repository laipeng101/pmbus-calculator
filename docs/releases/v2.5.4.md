描述成「需要器件 Profile / DIRECT 系数 / 设备数据」的规范解释级 P1；同一 PATCH 收口

> 2026-08-27 · PATCH（无新功能，文案与文档修正）· PMBus Rev 1.3 / SMBus 3.0

## 诚实声明：v2.5.3 的数学编码未错，错误在 Half 的 requirement 语义

v2.5.3 及之前所有版本的 L11/L16/DIRECT/HALF **数学编码、舍入与字节序全部正确且保持
不变**。缺陷只在文案与帮助层：独立 VOUT_MODE 页面在 `VOUT_MODE=0x60`（绝对 Half）时
同时显示状态「IEEE Half（需器件资料）」、警告「需要器件 Profile（DIRECT 系数/设备数
据）」、说明「DIRECT/Half … 需要器件系数（DIRECT m/b/R）或设备数据」——而同一页面的
L16 阻断卡却正确写明 IEEE Half 是合法标准格式。按 Part II §7.6/§8.4.4，Half 的
word ↔ 数值换算是标准 IEEE 754 binary16（bit15 符号、bits[14:10] 指数、bits[9:0]
尾数），**不依赖任何 m/b/R 系数、VID 表或器件 profile**；只有相对字节需要
VOUT_COMMAND 标称参考值（§8.5.2）。本版本不改变任何计算结果。

## Fixed

- **IEEE Half 被错误当成需要器件 Profile 的格式（P1）**：新增
  `src/app/vout-mode-requirements.ts` 的 `resolveVoutModeRequirement` 作为可穷举的
  discriminated requirement 单一来源，独立 VOUT_MODE 页面的状态文本、InfoPanel 警告、
  说明与计算步骤共同消费：
  - `0x60`（绝对 Half）：状态改为「IEEE Half（标准 binary16）」；warning 拆分为
    `vout-mode-half-standard`，表述「标准 IEEE 754 binary16（§7.6 / §8.4.4），换算
    不依赖器件数值，可在 HALF 模式页换算」；explanation 拆分为
    `half-standard-format`；全部表面反向禁词（`需器件资料`/`器件 Profile`/`m/b/R`/
    `DIRECT 系数`/`设备数据`），且不出现标称参考值要求；
  - `0xE0`（相对 Half）：payload 仍是标准 binary16，不要求任何器件数值；仅按 §8.5.2
    增加相对阈值需要 VOUT_COMMAND 标称参考值的表述；
  - `0x40`/`0xC0`（DIRECT）：继续明确要求器件 m/b/R 系数（§7.4，来自 COEFFICIENTS
    或器件资料），relative 组合再叠加标称参考值；
  - `0x61`/`0xE1`（Half/DIRECT 参数非零）：保持 invalid-parameter error 级与
    00000b 约束，不进入任何格式要求分支。
  - L16 页面 `half-unsupported-in-l16` 阻断卡文案本就正确，本版本仅以回归测试固定，
    未改动 L16 页为 Half 解码器（继续 fail closed，不借用 0x18）。
- **文档收口**：DOMAIN_MODEL §1 新增 §7.2/§8.1.2 设备级互斥（器件使用 Half 则所有
  numerical data 只能 Half；使用任一 LINEAR/DIRECT 则不得使用 Half——数据手册决定
  采用格式但不改变 binary16 解码公式）；§3 登记 requirement 单一来源合同；
  UI_CONVENTIONS §15 拆开合并的 DIRECT/Half 文案合同并新增 §16；两份 README 以 §7.2
  全设备互斥规则取代「器件可自由混用格式组合」的误导表述；ROADMAP 删除与已发布
  v2.5.3 矛盾的「发布进行中」过期状态。
