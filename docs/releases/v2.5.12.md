# PMBus Calculator v2.5.12

PATCH release：DIRECT 精确请求 provenance 修复与交付流程加固。

## 诚实陈述

1. **本修复是产品缺陷修复，不是 PMBus 公式变更，也不是器件精度提升。**
   PMBus Part II §7.4 的表示关系 `X = (Y×10^−R − b)/m` 与
   `Y = (mX + b)×10^R` 不变；仓库的 `Math.round`（half toward +∞）+
   signed16 clamp 编码策略不变（这是仓库合同，不是 PMBus 强制要求）。
2. **DIRECT exact request provenance 与 raw 编码现在共享同一词法真值**：
   v2.5.11 已用完整十进制 lexeme 精确编码 raw，但请求 provenance 与量化
   诊断仍退回 binary64，同一次事务出现两套真值——整数请求
   `100000000000000001`（m=1,b=0,R=−17）精确编码 `0001`，量化面板却报
   零误差且 status=exact；`-1.0000000000000000001`（m=1,b=1,R=17，精确
   误差 `-1e-19`）同样显示为零；精确越界
   `32767.0000000000000001` 被误判 exact 而非 saturated。现在 provenance
   保存 reducer 实际编码的同一 lexeme，量化分类与误差全部由精确有理数
   决定（范围端点取 signed16 Y 极值的精确解码，按 m 符号排序）。
3. **「精确」指被接受的 bounded lexeme**：只有完整、有限、长度 ≤4096 的
   十进制词法进入 exact 有理数路径；不是说「所有十进制都任意精度」。
   4096 上限是交互资源策略（依据：安全回录生成器 531,932 条文本实测
   最大 136 字符、理论上限约 607），不是 PMBus 规范限制。
4. **交付流程改动**：默认 5s 单测门禁消除确定性真实睡眠（契约测试注入
   backoff、`pow10` 记忆化、全量 sweep 拆分——语料与断言不减）；
   draft Release 资产的本地字节验证成为仓库正式入口
   `scripts/verify-downloaded-assets.mjs`，operator draft 门禁（元数据
   可接受 `untagged-<hex>` 占位）与 Pages published 门禁（严格 canonical
   tag URL 不放宽）共用同一实现，本地大小/checksum/ZIP 安全校验全部在
   解压、部署、publish 之前完成。

## 数值展示合同（DIRECT）

- 非零精确误差绝不渲染为文本零：`+1`、`-1e-19`、`+1e-16`（饱和）、
  `-1/6`（循环有理数分数）+ 「约」十进制近似；
- 相对百分比带内 4 位小数、带外科学计数法（`约 1e-15%`）；
- 面板与计算步骤共享同一 exact 渲染来源（DOMAIN_MODEL §2.3、
  UI_CONVENTIONS §15）。
